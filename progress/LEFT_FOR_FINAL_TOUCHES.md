### From Module 5.2 (Brand / Prompt Configuration)

- **RLS policies re-evaluate `auth.uid()`/`auth.jwt()` per row instead of once per query** (`auth_rls_initplan`, Supabase performance advisor WARN, 14 occurrences as of 2026-07-24). Affects every RLS-protected table in the project so far: `workspaces`, `workspace_members`, `user_profiles` (from migrations 0001-0004, pre-existing before this module), plus the three new tables this module added — `brands`, `competitors`, `prompts` (migration 0005). The fix is mechanical and well-documented by Supabase: wrap each `auth.uid()`/`auth.jwt()` call in a policy's `USING`/`WITH CHECK` clause as `(select auth.uid())`, which lets Postgres evaluate it once per query instead of once per row. Not a security issue (RLS still correctly denies cross-tenant access either way) — pure query-plan performance debt that only matters at real row-count scale, not with today's near-empty tables. Deliberately not fixed inline here: touching 5.1's already-`done`, already-tested policies as a drive-by inside a 5.2 commit would blur which module owns the change and risks re-breaking the RLS recursion fix from migration 0003 without a dedicated re-test pass. **Before real launch (or whenever query volume starts to matter):** write one migration that rewrites all 14 flagged policies with the `(select ...)` wrapper, then re-run `tests/integration/auth-rls.test.ts` to confirm behavior is unchanged.
- **Two `unused_index` / one `unindexed_foreign_keys` INFO-level advisor findings** — expected noise from near-empty tables (`brands_workspace_id_idx`, `prompts_brand_id_idx`, `competitors_brand_id_idx` haven't been used yet because there's no real traffic; `workspace_members.user_id` FK is pre-existing from 5.1, unrelated to this module). Not real debt yet — worth a second look only if they still show as unused once the app has genuine usage.
