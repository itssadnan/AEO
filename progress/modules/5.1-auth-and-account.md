- **2026-07-23** — One Free-plan workspace per person, not two, enforced via normalized-email uniqueness (not raw-string matching, which is trivially bypassed with +tag/dot email aliases) plus IP-based signup throttling. Deliberately did *not* add phone/card verification to close the remaining "two different real email addresses" loophole — that friction isn't justified against a threat this bounded, since ~~the Free plan itself is capped at 5 prompts/weekly checks regardless~~ (superseded same day — see entry below; Free plan redesigned to 3 lifetime experiments total, an even tighter bound). Rule scoped to Free-plan ownership only; workspace membership (agency clients invited as Viewer) is unrestricted.
- **2026-07-23** — Free plan redesigned from a recurring weekly-cadence tier to 3 lifetime on-demand experiments, then locked to read-only. This module owns `workspaces.experiments_used`'s creation/default only — cap enforcement and paid-feature gating live in the modules that actually run/limit checks. Full reasoning in `progress/modules/5.9-billing-and-subscription.md` decisions log.
- **2026-07-23 — Implementation.** Workspace creation (including the free-plan-uniqueness check) is a `SECURITY DEFINER` Postgres function (`create_workspace`), not a plain client-side `INSERT` into `workspaces` gated by RLS. **Why:** the uniqueness check has to read across `user_profiles`/`workspaces`/`workspace_members` and lock the matching `user_profiles` row (`FOR UPDATE`) to close a race between two concurrent signups for the same inbox — that's not expressible as a single RLS `WITH CHECK` clause, and doing the check-then-insert as two round-trips from the client would reopen the race. `workspaces` and `workspace_members` therefore have no client-facing `INSERT` policy at all; every workspace is created through this one function.
- **2026-07-23 — Implementation.** The Owner/Member/Viewer invite hierarchy (Owner invites any role, Member invites Viewer only, Viewer invites no one — see the historical decision this module inherited) is enforced as an RLS `INSERT` policy on `workspace_members` (`workspace_members_insert_by_role`), not only in application code. **Why:** per `docs/CONVENTIONS.md` Section 6 item 1, RLS is supposed to be the real gate, with app-level checks (`canInviteRole()` in `src/modules/auth/permissions.ts`) only deciding what the UI *shows* — this keeps that promise true for roles/invites specifically, not just for cross-tenant isolation.
- **2026-07-23 — Implementation.** Built the IP rate limiter (`rate_limit_events` table + `checkRateLimit()`) as a shared utility in `src/lib/security/`, even though this module only needs it for signup. **Why:** the acceptance criteria explicitly says "same pattern as the free-check tool (5.11)" — building it once now, generically, means 5.11 reuses it instead of re-implementing an equivalent table/function later.

- **2026-07-24 — Network access fixed; test actually run; found a real bug.** User fixed the sandbox's outbound network access. Re-ran `tests/integration/auth-rls.test.ts` via `node --env-file=.env.local --test`: it executed for real (no longer blocked) but **failed** — 3 of 4 subtests threw Postgres error `42P17: infinite recursion detected in policy for relation "workspace_members"`. The 4th subtest ("denies user B inserting...") shows as passing but its assertion is only `error !== null`, which the same recursion error also satisfies — it doesn't actually prove the intended denial. **Root cause, found in `app/supabase/migrations/0001_auth_and_workspaces.sql` lines ~159-218:** all four `workspace_members` RLS policies (`_select_same_workspace`, `_insert_by_role`, `_update_owner_only`, `_delete_owner_only`) check the caller's membership with a subquery that selects from `workspace_members` itself (`self`/`wm` alias) — a table checking its own membership by querying itself inside its own policy, which Postgres re-evaluates recursively. This also explains why even the plain `workspaces` read-only test failed: `workspaces`' own select policy joins into `workspace_members`, which triggers the broken policy. This is a known Supabase/Postgres RLS anti-pattern; the standard fix is a `SECURITY DEFINER` helper function (e.g. `is_workspace_member(p_workspace_id, p_user_id)`) that looks up membership with RLS bypassed internally, referenced from all four policies in place of the direct self-join. **Not fixed yet** — this is a live-database RLS change, so it needs a migration `0003` plus explicit user sign-off before applying, not an unprompted fix. The 4th subtest's assertion should also be tightened (check the specific Postgres error code for permission denial, not just "any error") so it can't false-positive the same way again.
