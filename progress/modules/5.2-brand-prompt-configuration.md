## Purpose
Where a customer defines what to track: brand, competitors, and buying-intent prompts.

## Acceptance criteria
- [x] Manual entry: brand name, website, competitor names — `create_brand_with_details()` RPC (migration 0006) + `BrandForm`/`brand-form.tsx`
- [x] AI-assisted prompt suggestion: one Gemini call proposes 20-30 prompts from the brand's site/industry — `suggestPrompts()` in `gemini.ts`, live-verified (see Verification below), returns 20-30 well-formed prompts
- [x] Free-plan workspaces: prompt list is auto-selected from the AI suggestions and fixed — not editable. Default chosen: **10** (see Decisions log for why 10, not some other number)
- [x] Paid-plan workspaces: full edit/add/remove on the prompt list, up to plan-tier prompt-count limits enforced server-side. Limits chosen: **Starter 25, Growth 75, Agency 200** (see Decisions log — picked specific numbers within the spec's stated ranges, and enforced **per-brand**, not per-workspace, a spec-underspecified interpretation call)

## Tech
Next.js form + Postgres.

## AI usage
One Gemini call per onboarding (one-time, not recurring). Direct REST call to `gemini-flash-latest`, deliberately not routed through the 5.3 `AIProvider`/`resolveTaskModel()` abstraction (see Decisions log).

## Caching
Not cached — this is low-frequency, user-driven write traffic.

## Security
Treat all user-entered prompt/brand text as untrusted; validate with zod and never interpolate raw into a system-level instruction to any AI call. Implemented: `brandName`/`website` passed to Gemini as a separate JSON data field, not string-concatenated into the instruction text (reduces, does not eliminate, prompt-injection risk via a malicious brand name). Model's JSON output is treated as untrusted: parsed, re-validated with zod (`promptSuggestionResponseSchema`), never rendered unescaped.

Real security boundary is DB-side, not app-side: `private.enforce_prompt_plan_rules()` (BEFORE INSERT/UPDATE/DELETE trigger on `prompts`) is the actual enforcement of plan-tier limits and Free-plan immutability. The zod schema in `schemas.ts` is a UX-only pre-check so the form can show an error before round-tripping to Postgres — if the two ever drift, the trigger wins (documented in the code comment).

## Decisions log
_(append-only — date, what was decided, why. Do not delete old entries even if superseded; strike through instead.)_

- **2026-07-23** — Free-plan workspaces get a fixed, non-editable prompt list; prompt customization becomes a paid-only capability. Part of the wider Free-plan redesign (3 lifetime on-demand experiments, then locked) — see `progress/modules/5.9-billing-and-subscription.md` decisions log for the full reasoning.
- **2026-07-24** — Chose concrete numbers within the spec's stated ranges: Free = 10 (spec said "kept low relative to Starter's floor" without a number; 10 is low relative to Starter's 25-floor and matches the Free plan's other "keep it small and bounded" choices — 3 lifetime experiments, no recurring scheduler). Starter = 25 (top of spec's 15-25 range — picked the generous end since the DB trigger is the real backstop regardless, so there's no cost to being generous in the app-facing number). Growth = 75 (top of spec's 50-75 range, same reasoning). Agency = 200 ("fair-use" in the spec, no number given — picked 200 as a concrete fair-use ceiling; can be raised via a workspace-level override later if a real Agency customer needs more, same override pattern 5.10 already plans for `ai_task_configs`).
- **2026-07-24** — Enforced prompt-count limits **per brand**, not per workspace. The spec doesn't explicitly say which; a workspace can contain multiple brands (5.1's data model), and it reads more naturally as "your Growth plan lets each brand you're tracking have up to 75 prompts" than "your whole workspace, across every brand you track, is capped at 75 prompts total" — the latter would make multi-brand tracking (an explicit agency use case per the spec) actively worse the more brands you add. Flagged as an interpretive call, not a literal spec instruction, so it's easy to revisit if it turns out wrong.
- **2026-07-24** — `create_brand_with_details()` written as `SECURITY INVOKER`, deliberately not `DEFINER` like 5.1's `create_workspace()`. Reason: real client-facing INSERT policies already exist on `brands`/`competitors`/`prompts` (`brands_insert_owner_or_member`, etc., migration 0005) — the RPC only exists to make a 3-table insert atomic in one round trip, not to grant any privilege the caller doesn't already have via RLS. `create_workspace()` needed `DEFINER` because no such INSERT policy exists on `workspaces`/`workspace_members` (see 5.1's decisions log) — different situation, different pattern, not an inconsistency.
- **2026-07-24** — `suggestPrompts()` calls the Gemini REST API directly (no SDK, no 5.3 `AIProvider`/`resolveTaskModel()` abstraction). Reason: 5.3's resolver/key-pool machinery exists for the *recurring, scheduled* grounded-search queries — this is a single one-time onboarding call per brand, with no grounding needed (brainstorming plausible buying-intent questions from the model's general knowledge, not answering as if it were a live search). Reaching into 5.3's not-yet-built abstraction from 5.2 would violate the module-boundary rule in `docs/CONVENTIONS.md` Section 1. If this call ever becomes recurring, it should move to go through `resolveTaskModel()` at that point — not before.

Not resolved; relied on tsc + prettier + tests as the substitute verification, consistent with this project's established tolerance for sandbox tooling flakiness — `.github/workflows/ci.yml` remains the real gate.

- **2026-07-24** — **Real bug, found post-`done`: every Vercel production build since this module's feature commit (`966cb69`) failed.** `brand-form.tsx` (a `"use client"` component) imported `PROMPT_LIMIT_BY_PLAN_TIER` — a runtime value — from the module's barrel `index.ts`, which also re-exports `suggestPrompts` from `gemini.ts` (`import "server-only"` at its top). Turbopack correctly refuses to bundle `server-only` code into a Client Component, regardless of whether that component actually calls the server-only export — importing *anything* from a barrel that re-exports it is enough to trip the check. This module's own "verified" claim above (tsc/prettier/tests passing) was true but incomplete: none of those three checks catch a client/server bundle-boundary violation, and `next build` itself SIGBUSes in this sandbox (Module 0.0's known limitation), so nothing available at the time could have caught this before Vercel's real build did. **Fix (commit `dcaabb3`):** moved the `PROMPT_LIMIT_BY_PLAN_TIER[planTier]` computation into `page.tsx` (a Server Component, safe to import the barrel) and pass the result down to `BrandForm` as a plain `limit: number` prop. `brand-form.tsx` now only has a standalone `import type { PlanTier } from "@/modules/brand-config"` — fully erased at compile time, creates zero runtime module-graph edge, so nothing from `gemini.ts` reaches the client bundle. `docs/CONVENTIONS.md`'s "single index.ts, nothing reaches in directly" rule is unaffected — `page.tsx` and `actions.ts`, both server files, remain the only importers of the barrel. **Verified live, not just locally:** confirmed via the Vercel MCP connector that deployment `dpl_CKgdoRRQvmitkBPgaF575Teof4wj` (commit `dcaabb3`) has `state: READY` and is aliased to production (`aeo-roan.vercel.app` is in its `alias` list, `aliasError: null`) — the first genuinely green production build since `966cb69`.
- **Lesson for future modules with both a client-facing form and server-only logic (AI calls, service-role DB access) in the same folder:** never let a Client Component import a runtime value from the module's barrel if that barrel also re-exports anything `server-only`-marked, even indirectly. Compute/fetch the needed value in the nearest Server Component ancestor and pass it down as a prop instead. `tsc`/`prettier`/unit tests will not catch this class of bug in this sandbox — only a real `next build` or an actual Vercel deploy will, so treat "pushed and Vercel shows READY" as part of this project's real Definition of Done for any module that adds a new Client Component, not optional follow-up.
