## Purpose
The core scheduler/worker: runs each active prompt against Gemini with Search grounding, on a schedule, and stores the raw result. Built behind an AIProvider interface so engines are swappable later.

## Acceptance criteria
- [ ] AIProvider interface defined; GeminiProvider is the only implementation for now
- [ ] ai_task_configs table + resolveTaskModel(taskKey, workspaceId) resolver owned by this module (global default row + per-workspace override, `enabled` flag, admin-only RLS — see ERD); no other module hardcodes a provider or model string
- [ ] Migration seeds global-default rows for all five task keys with the values from spec Section 6
- [ ] Queue-based worker pulls due (brand, prompt) pairs and calls Gemini with grounding enabled, resolving its model via resolveTaskModel("grounded_search", workspaceId)
- [ ] Full raw answer + citation list stored per check
- [ ] Throttled to Gemini's current free-tier RPM/RPD caps; checks staggered across the week, not fired all at once
- [ ] Retries with backoff on rate-limit errors; failed checks are requeued, never silently dropped
- [ ] Key pool (primary/secondary/tertiary) implemented for GeminiProvider and NvidiaNimProvider per docs/CONVENTIONS.md — 429 soft-fails to the next key, 401/403 marks that key dead + alerts the Admin Console, never a silent drop
- [ ] Falls back to the standard retry/requeue path if every key in a provider's pool is dead or exhausted
- [ ] Pool supports failoverMode "shared" (default; secondary/tertiary absorb 429s) vs "emergency-only" (secondary/tertiary called only on hard failures — 401/403/5xx/timeout, never a plain 429); switching to emergency-only is a one-flag change, not a redeploy of logic
- [ ] Admin Console (5.10) surfaces which failoverMode is active per provider and reminds the admin to flip it the moment primary is upgraded (billing enabled for Gemini, or the free 200 RPM increase for NVIDIA NIM)
- [ ] Free-plan workspaces never enter the recurring scheduler — checks are triggered on-demand by the user only, gated by `workspaces.experiments_used` (lifetime cap: 3, never resets); a 4th attempt is blocked outright with an upgrade prompt, never silently queued or allowed
- [ ] An on-demand free-tier check runs through the exact same AIProvider / resolveTaskModel / key-pool path as a paid check — no separate cheaper code path, since it is the same Gemini grounded call either way

## Tech
Supabase Edge Functions + pg_cron/pg_net (see decisions log, 2026-07-23 — Railway/Fly.io's free tiers are gone as of this date, so this is no longer an either/or; Edge Functions is the committed approach).

## AI usage
Google Gemini API, Grounding with Google Search.

## Caching
Paid plans: guard against redundant calls by verifying last_checked_at for that (brand, prompt) pair is older than the plan's check interval before enqueueing — a Postgres timestamp check, not a separate cache service. Free plan: no time-based guard applies (there is no recurring cadence) — instead gated by the `workspaces.experiments_used` lifetime counter, checked before allowing an on-demand run.

## Security
Gemini key is server-only, called exclusively from this worker, never from a client-reachable route. Log request counts, never prompt/answer content, in any cross-tenant-visible log.

## Decisions log
_(append-only — date, what was decided, why. Do not delete old entries even if superseded; strike through instead.)_

- **2026-07-23** — Split "swap AI vendor" from "swap model per task" into two layers: the `AIProvider` interface (vendor-level: Gemini/OpenAI/Perplexity/Copilot/NVIDIA NIM) and a new task-level config (which provider+model handles `grounded_search`, `extraction`, `explanation_generation`, `prompt_suggestion`, `outreach_email_drafting`). ~~Kept as a static file, not a DB table — no live-switching UI until there's an actual need for one.~~
- **2026-07-23 (same day, superseding the line above)** — Moved the task-level config from a static code file to a DB table (`ai_task_configs`) instead, because the actual requirement is an Admin Console UI that can enable/disable models per flow globally *and* set per-workspace overrides for custom-plan customers running model experiments — both need runtime editability a code file can't give without a redeploy. Provider API keys are unaffected by this change and stay in env vars only; the DB table stores model identifiers, never credentials. See `docs/CONVENTIONS.md` Section 5 and the entity-relationship diagram for the full design (resolution order, admin-only RLS, in-app caching with invalidation on write).
- **2026-07-23 — refinement: two failover modes, tied to the paid-tier upgrade trigger.** Proposed: once primary's account is upgraded (paid for Gemini, free RPM increase for NVIDIA NIM), it absorbs nearly all traffic, so secondary/tertiary (the teammate-owned accounts) should stop being used for ordinary rate-limit relief and become hard-failure-only fallback. This meaningfully reduces — but does not fully zero out — the risk accepted in the entry below, since the teammate keys remain wired in as emergency fallback. Target end state: once there's paying revenue, replace the teammate-owned secondary/tertiary with a second key the founder controls, fully retiring the third-party risk rather than carrying it indefinitely at a reduced rate. See docs/CONVENTIONS.md for the two-mode design.
- **2026-07-23 — Worker hosting: committed to Supabase Edge Functions + pg_cron/pg_net, dropping Railway/Fly.io as options.** Researched current (2026) free-tier status while answering a hosting question for Module 0.0: Railway no longer has a permanent free tier (only a 30-day $5 trial credit, then services pause); Fly.io no longer offers a free tier to new users either ($5/mo credit only). Both were the original candidates in this module's Tech line. Supabase Edge Functions remain genuinely free with a 150-second request timeout on the free tier — comfortably covers a grounded-search-plus-extraction chain per prompt — and require no new vendor account since Supabase is already the project's DB/auth provider. Scheduling via `pg_cron` invoking the function through `pg_net`, per Supabase's documented pattern.
  **Related, flagged for when 5.2 (prompt-suggestion) and 5.11 (free-check) are built:** Vercel Hobby's serverless function timeout is 10 seconds, hard-killed with a 504 past that. Anything in a Next.js API route that makes a *synchronous* AI call directly (the 5.2 "one Gemini call proposes 20-30 prompts" flow, and 5.11's public free-check) should budget for this — a single grounded-search call is typically a few seconds and likely fine, but should be measured once built, with the fallback of routing that specific call through a Supabase Edge Function (150s budget) instead of a Vercel API route if it ever gets close to 10s. Not a blocker now, nothing to implement yet — just don't assume unlimited synchronous request time on Vercel's free tier when 5.2/5.11 are built.
- **2026-07-23 — Free plan redesigned: 3 lifetime on-demand experiments instead of a recurring weekly cadence.** Previously the free tier ran the same recurring scheduler as paid, just weekly instead of daily — this left free-user AI quota consumption open-ended for as long as an account stayed signed up, stacking on top of the multi-key pool risk accepted below. Changed to: a Free-plan workspace gets exactly 3 lifetime on-demand checks (user-triggered, not scheduled), tracked by `workspaces.experiments_used` (see ERD) and gated here rather than left to the UI. After the 3rd run, 5.5 generates one aggregate report from the 3 data points and no further checks are allowed; 5.6 shows the existing report read-only plus an upgrade CTA. Paid plans are unaffected and keep the full recurring-scheduler behavior above. See `progress/modules/5.9-billing-and-subscription.md` decisions log for the complete before/after reasoning, and 5.5/5.6 for the corresponding Explanation-Engine and dashboard gating.
- **2026-07-23 — multi-key pool, risk explicitly flagged and accepted.** Decided to run each of Gemini and NVIDIA NIM behind a 3-key pool (primary/secondary/tertiary) during the free-tier period, using two additional accounts belonging to other team members alongside the founder's own. Before this was decided, the following was raised: (1) both providers enforce free-tier rate limits per account, so this only works with genuinely separate accounts, which is the exact pattern both providers' own abuse-monitoring treats as circumvention; (2) because all three keys are called from one backend for one product, detection is behavioral/pattern-based, not identity-based — it is expected to correlate and suspend all three accounts together if flagged, not one at a time, regardless of the fact that the accounts belong to real distinct people rather than fabricated identities; (3) a suspension would affect the account owner's personal use of that provider too, not just this product. The decision was made anyway, with the condition that every account owner has been told explicitly that their own account carries this risk. Scope: free-tier period only — this pool is removed once the product is funded onto a paid tier (the upgrade path already documented in spec Section 6.4). Required as a condition of this decision: dead-key detection must alert immediately (see acceptance criteria above and `docs/CONVENTIONS.md`), not fail silently.
