## Purpose

Aggregates results into the Visibility Score, Share-of-Voice, and the Explanation Engine (why a competitor wins + Opportunity Finder + confidence-tagged actions) — the product's flagship differentiator.

## Acceptance criteria

- [ ] Visibility Score (0-100), raw mention count, and average rank computed and stored
- [ ] Share-of-Voice vs named competitors, trended weekly
- [ ] Source Influence report (citation domains by type) computed
- [ ] Explanation Engine: percentage breakdown of why a competitor is cited more, via one NVIDIA NIM call per brand per check cycle, model resolved via resolveTaskModel("explanation_generation", workspaceId) against ai_task_configs — not hardcoded in this module
- [ ] Opportunity Finder: gap list of cited source types the brand has zero presence on
- [ ] Recommended actions are confidence-tagged (High/Medium/Low), never stated as flat guarantees
- [ ] Explanation Engine, Opportunity Finder, and recommended actions are computed only for paid-plan workspaces (`workspaces.plan_tier != 'free'`) — gated here, not just hidden in the UI, so Free-plan traffic never triggers the NVIDIA NIM call at all
- [ ] Free-plan workspaces get Visibility Score, mention count, average rank, Share-of-Voice, and Source Influence only; after the 3rd (final) lifetime experiment, one aggregate report is generated combining all 3 runs into a 3-point trend — still without the Explanation Engine

## Tech

Postgres aggregation (SQL) for scoring; one NVIDIA NIM call per brand per cycle for the explanation text.

## AI usage

NVIDIA NIM (same model class as 5.4).

## Caching

Aggregates (score, share-of-voice, explanation) are recomputed only when a new check result lands for that brand — cache the computed result and invalidate on new data, rather than recomputing on every dashboard load.

## Security

Recommendation text is model-generated — label it as guidance in the UI, never as a guarantee, to avoid overstating certainty to customers.

Confirmed exact requirements directly against the source docx's Section 5.5 (extracted via `python-docx`, not this file's condensed summary), plus Section 3.5 (Trust & Transparency Design Principle) and Section 4 (System Architecture Overview) for supporting context. **This module has no frontend component** — confirmed via the docx's own "Tech" line ("Pure SQL/backend aggregation for scoring and share-of-voice; one NVIDIA NIM call per brand per check cycle..."); Module 5.6 (Dashboard/Frontend) owns 100% of the UI/visual layer that will eventually display this module's output.
  Key architecture calls (full reasoning in the spec file):
  1. Unlike 5.3/5.4's "enqueue empty row, worker fills everything" pattern, a `visibility_snapshots` row is inserted **already containing** its real score/mention_count/avg_rank/share_of_voice/source_influence/opportunity_gaps — pure SQL, zero external dependency, computed synchronously. The status/queue/retry machinery applies **only** to the optional, paid-only explanation-prose sub-step.
  2. Trigger model: a periodic (every 30 min) cron scan for brands with fresh `check_extractions` data since their last snapshot, computing a rolling 7-day window — not a per-check trigger, to avoid over-scoring and to match this module's own caching note.
  3. This same freshness-check mechanism, unmodified, satisfies the Free-plan "3-point trend" acceptance criterion — no special-case code needed, since 3 sparse lifetime experiments naturally produce exactly 3 snapshot rows over time.
  4. The Explanation Engine's NVIDIA NIM call is restricted to **prose + confidence-tagged actions only, never a number** — a direct response to Module 5.4's live smoke test (2026-07-25), which found this model class doesn't reliably self-check literal facts even when explicitly instructed to. Every number here (score, percentages, the opportunity-gap list, the "winning competitor" determination) is deterministic SQL, computed before the model ever sees it.
  5. Extends `docs/architecture/entity-relationship-diagram.md`'s documented `visibility_snapshots` shape with `workspace_id`, `source_influence` (new — the ER diagram's current column list has no place for this distinct acceptance criterion), `explanation_skip_reason`, and the explanation-sub-step's queue/retry columns; the spec requires updating that ERD doc as part of the deliverable.

  The spec has a dedicated "lessons from 5.4's delegation" section addressing every real gap independent verification found in that module (hand-edited `database.ts`, an invented type, a false `.env.example` claim, unrelated files swept into a commit, unverified live-step claims) as explicit do-not-repeat items for whichever model implements this one.
