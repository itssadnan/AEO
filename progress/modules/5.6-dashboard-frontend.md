## Purpose

Customer-facing app: Overview, Prompt Explorer, Competitor Explorer, Reports, Settings — five views, not one monolithic page.

## Acceptance criteria

- [x] Overview: Visibility Score, raw mention count, average rank, Share-of-Voice trend; Free-plan workspaces additionally show remaining experiments (e.g. "2 of 3 free checks used")
- [x] Prompt Explorer: per-prompt drill-down + browsable AI Response History timeline
- [x] Competitor Explorer: Share-of-Voice always shown; Explanation Engine + Opportunity Finder panels render as a visible locked/upsell state for Free-plan workspaces (never silently omitted), full panels for paid
- [x] Reports: crawl-readiness checklist + exportable/white-label summaries (Agency plan)
- [x] Settings: brand/prompt config, team, billing portal link
- [x] Every result explicitly labeled by engine ("Gemini Visibility") with a one-click "How we calculated this" expansion
- [x] Free-plan workspaces past the 3-experiment cap: "run a new check" replaced with an upgrade CTA; all previously generated report data remains fully viewable — read access is never revoked

## Tech

Next.js + TypeScript + Tailwind, deployed on Vercel.

## AI usage

None directly — renders data other modules computed.

## Caching

Use Next.js data cache with tag-based revalidation, invalidated when a new check result lands for that brand — avoids recomputing/refetching on every page view between check cycles.

## Security

CSRF protection on forms; all AI-sourced text (answers, explanations) rendered via safe text components, never dangerouslySetInnerHTML — it is untrusted third-party content.

## Decisions log

- **2026-07-23** — Competitor Explorer shows a visible locked/upsell state for Explanation Engine/Opportunity Finder on Free-plan workspaces rather than hiding the panels outright, and the Overview surfaces remaining free-experiment count. Part of the wider Free-plan redesign — see `progress/modules/5.9-billing-and-subscription.md` decisions log.
- **2026-07-26** — Full implementation spec written: `progress/specs/5.6-dashboard-frontend.md`, per Heisenberg's request for a design brief grounded in real competitor research plus an implementation spec. Key decisions, full reasoning in the spec file:
  1. **Design system grounded in direct research**, not generic taste: read the spec docx's own named competitor list (Section 2.3 — KIME, Profound, Peec AI, Semrush AI Toolkit, Otterly.AI, Nightwatch, SE Visible, AirOps, Searchable) and researched the top few directly (Profound's near-black `#08090A` enterprise UI, Peec AI's four-area structure that's nearly identical to this module's five-view split — and its consistently-documented weakness of overwhelming first-time users with no onboarding, which this spec explicitly designs around via first-class empty states — Otterly.AI's single-benchmark-number philosophy), plus 2026 SaaS-dashboard design-pattern research (progressive disclosure as the dominant pattern across Linear/Vercel/Stripe/Notion/Supabase/Raycast/Sentry). Synthesized into a specific, opinionated system: dark-mode-first with a true near-black surface scale (never pure black), a single deliberately-not-blue violet-indigo accent (`#6E5BFF`) to stand out in a category where every competitor leans neutral-dark or blue, Geist Sans/Mono (already a project asset via `next/font`, not a new dependency) with tabular numerals for all data figures, borders-not-shadows elevation, and a reusable `CalculationDisclosure` component as the single, polished implementation of the Section 3.5 Trust & Transparency requirement — treated as the product's actual point of differentiation, not an afterthought link, since Section 2.3 is explicit there's no technology moat in this category and the UI/trust experience is one of the few places left to compete.
  2. **A dedicated "lessons from 5.4 and 5.5" section**, per explicit request, compiling every real defect independent verification found across both prior delegations (not hypothetical risks): self-reports being wrong even when code is right, satisfying the *letter* of an instruction with an unrelated fix instead of the actual one asked for, inventing unrequested fields/design choices instead of flagging ambiguity, duplicating an existing shared utility instead of reusing it, spec-provided reference material itself containing real bugs (an invalid Postgres construct and a nonexistent Vault function, both copied in verbatim from 5.5's own spec and only caught by live execution), and Module 5.2's real documented incident where a client/server bundle-boundary bug passed every static check and only a live Vercel build caught it — directly relevant here since this is the first module doing real Client/Server Component composition at scale. Extended one lesson specifically for this module: never let the frontend recompute a number the backend already computed (the same principle 5.5's SQL-only-computation design was built around, one layer up the stack).
  3. **Flagged, not silently resolved: `progress.json` lists this module's only dependency as `5.3` (`in_progress`, 98%), but its actual acceptance criteria need `5.4` (`done`) and `5.5` (`in_review`) data to render anything real.** Spec instructs the executor to build against the real schema regardless and treat near-empty current data (one real `visibility_snapshots` row in the whole database) as the expected first-run case to design for, not an edge case — and to flag the dependency-list gap in its report rather than quietly building around it or blocking on it.
  4. **New folder introduced**: `app/src/components/ui/` for cross-view presentation-only primitives, since `docs/CONVENTIONS.md`'s existing folder structure (Section 1) has no place for shared UI components that aren't a single module's business logic — spec instructs the executor to add one documenting paragraph to CONVENTIONS.md as part of this module's deliverable, keeping that doc in lockstep per this project's central rule, the same way 5.5 extended the ER diagram.
  5. **Status/percentComplete intentionally left unchanged** (`not_started`/0) — a spec is not an implementation, same reasoning as 5.5's own spec-writing entry.
