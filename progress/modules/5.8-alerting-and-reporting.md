## Purpose

Keeps customers engaged between logins: a weekly email digest (score change,
new/lost mentions, new crawl issues) and threshold alerts (a named
competitor newly cited where the brand wasn't — Growth+ plans).

## Acceptance criteria

- [x] Weekly digest: score change, new/lost mentions, new crawl issues (`get_weekly_digest_candidates()`, migration 0021, live-tested with synthetic data — see decisions log)
- [x] Threshold alert: competitor newly cited where customer wasn't (Growth+ plans) (`get_new_threshold_alerts()`, migration 0021, live-tested)
- [ ] Real email actually delivered to a real inbox — cannot be verified until the user creates a Resend account and sets `RESEND_API_KEY`/`ALERTING_FROM_EMAIL` (see Blockers); the code path is complete and was verified to correctly no-op (not error, not falsely mark-as-sent) when the key is absent

## Tech

Resend (free tier: 3,000 emails/month), triggered weekly by pg_cron/pg_net calling the `alerting-worker` Supabase Edge Function — same architecture as the 5.3/5.4/5.5 workers.

## AI usage

None. Spec Section 5.8 lists an *optional* one-sentence plain-English AI summary of the week's numbers — deliberately not implemented in this pass (see decisions log): every AI provider in this project is already quota-constrained (see Module 5.3's ongoing blocker), and this is explicitly the one piece of this module's scope the spec itself marks optional. The digest is fully useful without it (real score/mentions/crawl-issue data, not placeholder text). Revisit once 5.3's quota situation is resolved.

## Caching

Not cached — this module reads already-computed data (`visibility_snapshots`, `check_extractions`, `crawl_audits`) once per cron tick; there's nothing to cache. The idempotency guard (`alert_logs`'s unique `(brand_id, type, dedupe_key)` index) is a dedupe mechanism, not a cache.

## Security

- `get_weekly_digest_candidates`, `get_new_threshold_alerts`, `record_alert_sent` read email addresses (`user_profiles.raw_email`) and cross-brand data — revoked from `public`/`anon`/`authenticated`, granted to `service_role` only, same as `ai_task_configs`'s admin-only pattern (docs/CONVENTIONS.md Section 5).
- `alert_logs` RLS: workspace members can read their own brand's alert history; no client insert/update/delete policy (append-only log, written only by `record_alert_sent`).
- `alerting-worker` authenticates via `ALERTING_WORKER_SECRET` (Vault + Edge Function secret), constant-time comparison — same pattern as every other worker.
- All user-entered text (brand name, competitor name, prompt text) is HTML-escaped before being interpolated into generated email HTML (`escapeHtml()`, tested against real script-injection payloads in `alerting-render.test.ts`) — this is the "untrusted content" rule from docs/CONVENTIONS.md Section 6, applied to an email body instead of a rendered web page.
- SPF/DKIM/DMARC on the sending domain: not yet configured — blocked on the Resend account/domain existing at all. Tracked explicitly in Blockers, not silently skipped.

## Blockers

- **User action required, cannot be completed by Claude under any authorization (same category as Module 5.3's remaining blocker):** real email delivery requires (1) creating a Resend account and setting `RESEND_API_KEY`/`ALERTING_FROM_EMAIL` to real values, and (2) setting `ALERTING_WORKER_SECRET` as a real Edge Function secret (the Vault-side value already exists; only the Edge Function's own copy is missing, and no available tool can set Edge Function secrets). Both are credential/secret-entry actions that either fall under this environment's "never enter a financial credential/API key/token into any field" rule, or are simply outside what any available tool can do. The worker deploys and runs safely today — it computes real candidates and cleanly logs a skip (never a false "sent") when `RESEND_API_KEY` is absent, exactly like every other worker's "code is done, one secret is left" completion state in this project.
- SPF/DKIM/DMARC DNS records on the sending domain — needed before real mail delivers reliably (docs/CONVENTIONS.md Section 6). Also the user's own action once a domain is chosen for sending.
- No genuinely "live" (non-synthetic) weekly digest or threshold alert has fired yet, since (a) no paid Growth+/Agency workspace with real qualifying data currently exists in production, and (b) Module 5.3's ongoing grounding-quota blocker means very little fresh `check_extractions`/`visibility_snapshots` data is landing at all right now. The functions are proven correct against synthetic data; a first genuine production send is still pending both this module's own Resend setup and 5.3's unrelated quota resolution.
