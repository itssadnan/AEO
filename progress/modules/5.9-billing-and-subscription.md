## Purpose
Razorpay Checkout + Subscriptions API for signup/recurring billing; self-serve plan-change/cancellation UI built in-house; enforces plan-tier limits.

## Acceptance criteria
- [ ] Razorpay Checkout + Subscriptions API for signup and recurring billing
- [ ] Self-serve plan change/cancellation UI (built in-house — Razorpay has no hosted Customer Portal equivalent to Stripe's)
- [ ] Webhook listener updates plan tier and enforced limits in the DB
- [ ] Prompt-count/frequency limits enforced in 5.2 and 5.3, not just displayed in the UI
- [ ] Free plan enforces a lifetime cap, not a period-based one: `workspaces.experiments_used` capped at 3, never reset by this module's billing-period logic (that reset logic applies to paid plans' `usage_counters` only)
- [ ] Upgrading a Free-plan workspace to any paid tier does not reset or restore `experiments_used` — it becomes irrelevant the moment `plan_tier` leaves `free`, since paid plans aren't limited by it

## Decisions log
_(append-only — date, what was decided, why. Do not delete old entries even if superseded; strike through instead.)_
- **2026-07-23** — Switched billing gateway from Stripe to Razorpay.
  **Why:** Stripe has been invite-only for India-registered businesses since May 2024 and remains so as of mid-2026 (confirmed on Stripe's own India FAQ, support.stripe.com/questions/india-faq) — no self-serve signup, approval not guaranteed. Razorpay offers instant self-serve onboarding, $0 setup fee, $0 AMC, and ~2% domestic / 3% international transaction fee (vs Stripe's 2.9%+$0.30 domestic plus ~1.5–2% international/FX surcharges, plus a 0.7% fee if using Stripe Billing for recurring plans). Razorpay's Subscriptions API + Node.js SDK fit the existing TypeScript/Next.js stack cleanly.
  **Trade-off to remember:** Razorpay has no hosted Customer Portal like Stripe's — the self-serve "change plan / cancel" UI has to be built in-house on top of Razorpay's Subscriptions API rather than dropped in as a vendor-hosted page. Budget dev time for this in module 5.9 implementation.
  **Revisit if:** international customer volume grows enough that VAT/sales-tax compliance in other countries becomes material — at that point, evaluate adding a Merchant-of-Record layer (Dodo Payments or Paddle) on top of/instead of Razorpay rather than treating this as settled permanently.
- **2026-07-23** — Found and fixed a staleness bug while updating 5.10: `docs/architecture/entity-relationship-diagram.md` still had `stripe_customer_id`/`stripe_subscription_id` columns and `system-architecture.md` still said "based on Stripe subscription state" — both left over from before this module's Stripe→Razorpay switch above. Renamed to `razorpay_customer_id`/`razorpay_subscription_id` and updated the prose to match. No functional change, just closing the gap between this decision and the architecture docs.
- **2026-07-23** — User decided to deliberately defer this entire module — both the Razorpay test-mode account creation and the 5.9 integration work — until after core product features (5.1-5.8) are built, rather than setting it up during initial project setup (0.0).
  **Why:** prioritize getting the actual visibility-tracking product working before wiring up billing; billing only matters once there's something to charge for.
  **Impact check:** safe to defer — 5.9 depends on 5.1 (satisfied whenever 5.1 finishes) but only blocks 5.10 (Admin Console's revenue view), which itself isn't needed until there are paying customers. Nothing in the 5.1-5.8 critical path depends on 5.9.
- **2026-07-23 — Free plan redesigned: 3 lifetime on-demand experiments + one report, then locked, replacing the original recurring-weekly-checks-forever model.**
  **What changed:** a Free-plan workspace no longer gets an ongoing weekly automated check. It gets exactly 3 on-demand, user-triggered checks total (never resets, doesn't renew), tracked by a new `workspaces.experiments_used` column (see ERD). After the 3rd run, 5.5 generates one aggregate report (score, rank, citations, a 3-point Share-of-Voice trend) and no further checks are allowed. Paid plans (Starter/Growth/Agency) are unaffected — they keep recurring automated checks (weekly/daily by tier) and their existing period-based `usage_counters` limits.
  **What's also paid-only now:** the Explanation Engine, Opportunity Finder, and confidence-tagged recommended actions (5.5) are computed only for paid plans — not just hidden in the UI, gated before the NVIDIA NIM call happens at all, since that call is the product's second real AI cost per cycle. Free-plan prompts also become fixed/non-editable (5.2) — prompt customization is a paid unlock.
  **Why:** the original free tier's AI-quota exposure per signup was open-ended — a free account could keep drawing weekly Gemini + NIM calls indefinitely for as long as it stayed signed up, compounding the risk already accepted around the multi-key failover pool (see `progress/modules/5.3-engine-query-engine.md` decisions log). A fixed lifetime cap bounds the cost of every free signup to a known, small number. It also removes an entire scheduling branch from 5.3 — Free workspaces never enter the recurring scheduler at all, only paid ones do — and creates a harder, clearer upgrade trigger (a visible countdown) than an ambient, low-frequency tier a user could sit on indefinitely without ever feeling pressure to upgrade.
  **Superseded:** spec Section 3.3/3.4's "Automated weekly (free plan) / daily (paid plan) checks" line is superseded by this decision for the Free plan specifically; paid-tier numbers (Starter 15-25, Growth 50-75, Agency fair-use) are unchanged. The spec docx itself is left as the original v1.1 historical document, not live-patched — this tracker entry is the current source of truth for the Free plan going forward, per this repo's usual pattern (see the Stripe→Razorpay entry above).
  **Cross-references:** enforcement split across 5.2 (fixed prompt list), 5.3 (on-demand trigger + counter gate, no scheduler), 5.5 (aggregate report + paid-only Explanation Engine), 5.6 (locked/upsell UI state, remaining-count display, read-only access after cap), this module (lifetime vs. period-based limit distinction). `workspaces.experiments_used` column owned/created by 5.1.
