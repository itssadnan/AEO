## Security

- Every Razorpay webhook verified via HMAC-SHA256 signature (constant-time compare via `node:crypto`'s `timingSafeEqual`) over the **raw, unparsed** request body before the payload is trusted or even JSON-parsed; unverified webhooks rejected with `400` before touching the DB. Unit-tested against a real correctly-signed payload, a tampered body, a wrong-secret signature, a missing header, and a malformed/short header (no crash).
- Idempotent via `record_webhook_event` (migration 0023), keyed on a synthesized `event:subscription_id:created_at` id, since Razorpay documents at-least-once webhook delivery.
- `RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` are server-only — `razorpay-client.ts` and `webhook-verify.ts` both carry a `server-only` import guard, so an accidental client-bundle import is a build-time error, not a code-review convention. No Razorpay secret is ever sent to the browser; the client only ever receives `razorpayKeyId` (the public key id) and a subscription id from a Server Action's return value — exactly what Razorpay's Checkout.js script needs client-side, and both are safe to expose.
- `update_subscription_from_webhook`/`record_webhook_event` are locked to `service_role` only (`revoke ... grant ... to service_role`, migration 0023) — the webhook route has no Supabase session (Razorpay's call carries none), so it authenticates purely via the HMAC signature check, then acts with the service-role client.
- `create_pending_subscription` is `SECURITY DEFINER` but callable by `authenticated`, with its own explicit `auth.uid()` + `has_workspace_role(..., 'owner')` check inside — re-checked a second time in `actions.ts`'s `requireWorkspaceOwner()` for defense in depth, so an unauthorized caller gets a clean `{ error }` instead of a raw Postgres `FORBIDDEN`/`42501` string.
- Webhook route has **no IP rate limit or captcha**: HMAC signature verification is the actual abuse guard for a webhook endpoint (docs/CONVENTIONS.md's rate-limit DoD item is aimed at public/unauthenticated *user-facing* endpoints — a captcha is meaningless against a server-to-server webhook call, and Razorpay does not publish a stable IP range suitable for an allowlist).

- **2026-07-31 — Razorpay subscriptions require a bounded `total_count` even for "until cancelled" billing** (no literal infinite option in their API) — used 120 monthly cycles (10 years). ## Blockers

- **User action required, cannot be completed by Claude under any authorization** (entering financial credentials/API keys is a hard-prohibited action for this environment, not a style preference, and applies identically to Module 5.3's Gemini keys and 5.8's Resend account before it): real billing needs (1) a real Razorpay account with `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` (Dashboard > Settings > API Keys), (2) `RAZORPAY_WEBHOOK_SECRET` (Dashboard > Settings > Webhooks — create a webhook pointed at `https://<domain>/api/webhooks/razorpay`, subscribed to the `subscription.*` events), and (3) `RAZORPAY_PLAN_ID_STARTER`/`GROWTH`/`AGENCY` (Dashboard > Subscriptions > Plans, one Plan per tier — price each per `modules/billing/plans.ts`'s `priceInrPaise`, then reconcile that placeholder constant with whatever the real Plan ends up configured with). Every Server Action in `modules/billing` checks `isRazorpayConfigured()` first and returns a clean `{ error }` — no crash, no silently-fake success — when these are unset. The app deploys and runs safely today with billing cleanly disabled until they're set.
- No genuinely live (non-synthetic) checkout, webhook delivery, or plan-tier flip has happened yet, since there is no real Razorpay account to test against. The DB functions and webhook-parsing logic are proven correct against synthetic/unit-test data; a first real end-to-end payment is still pending the account setup above.
