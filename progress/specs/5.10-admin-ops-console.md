## Read this first — lessons from this project's delegation history (apply these here, don't repeat them)

Every item below actually happened on a real module in this project (5.6, 5.7) and was caught only because Claude independently re-verified the delegate's self-report against ground truth rather than trusting it. This module gets the same treatment; write your report accordingly.

1. **A "done" checklist with a fabricated or inconsistent test count is worse than no checklist.** Only report a number you got by actually running `npm test` (this project's real test command is `tsx --conditions=react-server --test tests/unit/*.test.ts` via `node:test` — **not vitest**, despite a `vitest.config.ts` existing in the repo; see Module 5.7's decisions log for the full story of a test file that silently never ran for months because it imported `vitest`'s API under the wrong runner) in that exact session and pasting the real output.
2. **Client Components importing anything from a module barrel that also re-exports server-only code breaks the production build**, invisibly to `tsc`/tests/lint — a real, repeated incident (Module 5.2, then twice on Module 5.7). `docs/CONVENTIONS.md` Section 1 now has a documented exception for this; read it and follow it if this module's admin UI needs to share any pure logic with its own Client Components. This module's routes are almost entirely Server Components/Server Actions (internal-only, no reason for heavy client interactivity beyond simple forms), so this risk should be low here if you keep interactive bits (a "clear dead key" button, a failover-mode toggle, an inline edit form) as small, focused Client Components that only ever import Server Actions and plain types — never a function that itself touches `@/lib/db`.
3. **Copy-pasting the same logic into multiple files instead of extracting one shared function** has caused a real, shipped billing bug before (Module 5.6's `mapPlanTier`). If two admin views need the same formatting/threshold logic (e.g. "is this key's quota near its cap"), write it once as a pure function in this module's folder and import it.
4. **`any` without the required inline justification comment is a Definition-of-Done violation**, not a style nit (`docs/CONVENTIONS.md` Section 2). This module reads `jsonb`/loosely-typed error/metadata columns in a few places (see "Shapes" below) — every one of those needs either a real type or a justified, commented `any`.
5. **This project's delegates have a repeated pattern of writing correct logic that is never actually wired into its caller** (Module 5.7, three consecutive rounds: an unrendered component, then an unused caching function, then an unused checklist function). For this module specifically: if you add `resolveTaskModel`'s admin-edit UI, the RPC/route/action, and the actual page.tsx section, **all three must exist and actually call each other** — a correct Server Action nobody's button calls is the same as it not existing. Report exactly which page renders which section and calling which action, with file:line references, not just "implemented X."
6. **`docs/architecture/entity-relationship-diagram.md` and `progress/progress.json`/the module's own tracker file are part of the deliverable, not an optional follow-up** — Module 5.7's own spec required this and it's required again here (see "Read before writing any code" item 3 above).

## Admin gating

There is no admin-role concept anywhere in this codebase today (confirmed: `user_profiles` has no `is_admin`/role column, and no admin allowlist exists in code or env). Per the spec docx's "Tech" line ("protected by an admin flag on the founder's own account — not a separate product") and this being a two-person, pre-revenue team, use a **server-only env-var allowlist**, not a new database table/column/migration:

```typescript
// app/src/lib/security/admin.ts (NEW — alongside the existing rate-limit.ts
// and ssrf-guard.ts in this same folder, same pattern)
import { normalizeEmail } from "@/modules/auth"; // reuse, do not reimplement
import { createSupabaseServerClient } from "@/lib/db";

/**
 * Returns null if the currently signed-in user's normalized email is in
 * ADMIN_USER_EMAILS (server-only env var, comma-separated, never
 * NEXT_PUBLIC_). Returns an error object otherwise. Call this at the top
 * of every admin Server Action AND in the admin route's page.tsx (defense
 * in depth — docs/CONVENTIONS.md Section 6 item: "Gate at the server/API
 * layer by role check, not just by hiding a frontend link").
 */
export async function requireAdmin(): Promise<{ error: string } | null> {
  const supabase = await createSupabaseServerClient();
  const {
    data: { user },
  } = await supabase.auth.getUser();
  if (!user?.email) return { error: "You must be signed in." };

  const allowlist = (process.env.ADMIN_USER_EMAILS ?? "")
    .split(",")
    .map((e) => e.trim())
    .filter(Boolean)
    .map(normalizeEmail);

  if (!allowlist.includes(normalizeEmail(user.email))) {
    return { error: "Not authorized." };
  }
  return null;
}
```

Add `ADMIN_USER_EMAILS` to `app/.env.example` (comma-separated list, comment explaining it's the founder's own account(s), no default value — an empty allowlist should deny everyone, never fail open).

`app/src/app/admin/page.tsx` (the route's Server Component) calls `requireAdmin()` first and calls Next's `redirect("/")` (or renders a plain "Not authorized" message — your choice, but it must not render any admin data) if it returns an error. Every Server Action in this module's `actions.ts` also calls `requireAdmin()` independently at its own top — do not rely on the page-level check alone, since a Server Action can in principle be invoked directly.

All reads/writes this module performs against `ai_task_configs`, `ai_provider_key_health`, `ai_provider_settings`, and `engine_error_logs` use the **Supabase service-role client** (`createSupabaseServiceRoleClient` — check `app/src/lib/db/index.ts` for the exact existing export name), because — per `docs/CONVENTIONS.md` Section 5 verbatim — "`ai_task_configs` ... is the one exception to the standard RLS pattern... Only server-side Admin Console routes (using the Supabase service role, which bypasses RLS) touch this table." The other three tables you'll confirm (via `list_tables`) have RLS enabled with **zero policies defined** — this is not a bug to fix, it is the correct, already-intentional posture (deny-all via PostgREST to anyone except service-role). Do not add RLS policies to any of these four tables. `requireAdmin()` is the only access control this module needs or should add.

## Alerting (the "immediate alert" acceptance criterion)

The acceptance criterion "A key transitioning to dead (401/403) fires an immediate alert, not just a log line" has no channel to fire through yet — Module 5.8 (email digests/alerts) is deferred pending a Resend account and DNS records that don't exist. Do not block on 5.8 or invent an email send here. Instead:

- Add an optional, server-only `ADMIN_ALERT_WEBHOOK_URL` env var (documented in `.env.example` as optional, e.g. a Slack or Discord incoming-webhook URL the founder already has — no new vendor account required if they already use either).
- In the engine-worker's `markKeyDead` function (both the Next.js-side mirror in `app/src/lib/ai-providers/key-pool.ts`'s test-covered logic path and the live Deno copy in `app/supabase/functions/_shared/key-pool.ts` — see "Worker change" below for why both exist and must stay in sync), after the existing `mark_ai_key_dead` RPC call succeeds, if `ADMIN_ALERT_WEBHOOK_URL` is set, `POST` a small JSON body (`{ text: "AI provider key dead: {provider} {slot} ({code})" }` — Slack/Discord-compatible shape) to it, with a short timeout (e.g. 5s) and a `try/catch` that only logs on failure — a webhook failure must never fail or retry the underlying job.
- If the env var is unset, this is a silent no-op (not an error) — the dead-key event is still fully recorded in `ai_provider_key_health` and `engine_error_logs`, and visible immediately in this module's own Admin Console UI, which is itself a real (if pull-based, not push-based) alert surface. State plainly in your report that the webhook is optional and what happens when it's unset.

## Worker change (touches Module 5.3's engine-worker — read carefully, this is the one part of this spec outside this module's own folder)

**Goal:** make `check_runs` record which key slot (primary/secondary/tertiary) actually handled each successful request, so this module's quota-consumption view can be broken down per key, not just per provider — the acceptance criterion's literal wording. Today, nothing records this for successful/ordinary-retry requests (only dead-key events do, via the already-correct `mark_ai_key_dead` path).

**Design — success path only, add an `onAttempt` callback, do not touch `AiProviderError`:**

1. `app/src/lib/ai-providers/key-pool.ts` **and** `app/supabase/functions/_shared/key-pool.ts` (keep both copies identical — same rule as every prior change to this file, see the comment already at the top of `key-pool.ts` explaining why the copies exist and must not drift): add an optional `onAttempt?: (slot: KeySlot) => void` field to `withKeyFailover`'s options, and call it (synchronously, before calling `options.run(candidate.key, candidate.slot)`) at the start of each candidate attempt in the `for` loop. **Do not** modify `AiProviderError`'s constructor — that class has an explicit existing comment explaining why it must stay a plain constructor body for the Node test runner; leave it untouched.
2. `app/supabase/functions/_shared/gemini-provider.ts` and `nvidia-nim-provider.ts`: accept an optional `onAttempt` in their own options and pass it straight through to `withKeyFailover`.
3. `app/supabase/functions/engine-worker/index.ts`'s `runProviderCall`: declare a local `let lastAttemptedSlot: KeySlot | undefined;` before calling either provider function, pass `onAttempt: (slot) => { lastAttemptedSlot = slot; }`, and return `lastAttemptedSlot` alongside the existing `{ text, citations, groundingMetadata }` shape (add a `keySlot` field to the return type).
4. `processJobWithStagger`: on the success path, pass `result.keySlot` as a new `p_key_slot` argument to `complete_check_job`. On the failure path (the `catch` block), `lastAttemptedSlot` is not in scope there today — hoist it the same way `provider` already is (see the existing `let provider: "gemini" | "nvidia_nim" = "gemini";` hoisted above the `try` block, with its own explanatory comment) so the last slot attempted before final failure is available to pass as `p_key_slot` to `retry_or_fail_check_job` too. If no attempt was made at all before failing (e.g. `not_configured` — every key missing), leave it `undefined`/`null`; do not fabricate a slot.

**Migration (`app/supabase/migrations/0019_admin_ops_console.sql`):**

-- key (primary/secondary/tertiary), not just per provider. Nullable --
-- historical rows and any future failure where no key was ever attempted

-- with an added optional param is signature-compatible and safe here, same
-- pattern already used by migration 0009 to add p_provider to
-- retry_or_fail_check_job. Do NOT create a second overload (migration 0011

create or replace function public.complete_check_job(

create or replace function public.retry_or_fail_check_job(
  p_job_id uuid, p_error_code text, p_retry_after_seconds integer default 60,
  p_provider text default 'gemini', p_key_slot text default null
)
returns void language plpgsql security definer set search_path = public as $$
declare j public.check_jobs; v_retry boolean;
begin
  select * into j from public.check_jobs where id=p_job_id and status='processing' for update;
  if not found then return; end if; v_retry := j.attempts < 5;

  insert into public.engine_error_logs(provider,job_id,error_code,retryable,key_slot) values(p_provider,p_job_id,p_error_code,v_retry,p_key_slot);

-- existing grants, but the exact signature in the revoke/grant statements

grant execute on function public.complete_check_job(uuid,text,text,text,jsonb,jsonb,text) to service_role;
revoke all on function public.retry_or_fail_check_job(uuid,text,integer,text,text) from public, anon, authenticated;
grant execute on function public.retry_or_fail_check_job(uuid,text,integer,text,text) to service_role;

## Route (`app/src/app/admin/page.tsx`)

One internal Server Component page (per the spec docx: "not a separate product" — do not build a nested route tree with sub-pages/tabs-as-routes; use in-page sections or client-side tabs within a single route if you want visual separation). Calls `requireAdmin()` first; if it errors, render a plain "Not authorized" message (do not leak *why* beyond that — do not distinguish "not signed in" from "signed in but not an admin" in the rendered UI, to avoid giving a non-admin any information about the allowlist's existence/shape). If authorized, fetch all six `get*` functions above (a `Promise.all`, same pattern as `reports/page.tsx`) and render sections:

1. **Quota** — per provider, per key slot, request counts (last 1h, last 24h) next to the informational cap from `KNOWN_FREE_TIER_CAPS`, visually flagged (e.g. a warning color, reuse existing tokens) when `isNearCap` is true.
2. **Key health** — a small table: provider, slot, alive/dead, dead-since, last error code, a "Clear dead flag" button (Client Component calling `clearDeadKeyAction`) shown only when dead.
3. **Failover mode** — current mode per provider, with the reminder text from the acceptance criteria ("switch to emergency-only once primary is upgraded to paid/higher-tier") always visible, and a toggle (Client Component calling `setFailoverModeAction`).
4. **Error log** — most recent N (choose a reasonable page size, e.g. 50) from `getErrorLog`, newest first.
5. **Churn signal** — customers inactive 2+ weeks, per `getChurnSignal(14)`.
6. **AI task configs** — a table of every row from `getAiTaskConfigs` (global defaults first, then overrides grouped under their task), each editable inline (Client Component form calling `upsertAiTaskConfigAction`), plus a way to add a new per-workspace override (a workspace picker — reuse whatever existing workspace-search pattern this codebase already has, check `app/src/modules/dashboard` or `app/src/app/(dashboard)` first before inventing a new one) and remove one (`deleteWorkspaceOverrideAction`).

Caching: per `docs/CONVENTIONS.md` Section 4's own row for this exact page ("Short TTL (e.g. 60s)... a slightly stale read is an acceptable tradeoff") — do the simplest thing that satisfies this: either a short `revalidate` on the route segment or no caching at all with a manual refresh button; do not build a custom cache layer for an internal page nobody hits at volume. State which you chose and why in your report.

## Tests (`app/tests/unit/admin.test.ts`)

Use `node:test`/`node:assert/strict` — this project's real test runner (see lesson 1 above; do not import from `vitest`). Follow the existing style in `app/tests/unit/dashboard.test.ts` or `crawl-audit.test.ts`. Minimum coverage, success and failure paths both required:

- `requireAdmin()`: given a mocked signed-in user whose email is in a test `ADMIN_USER_EMAILS`-equivalent list (set the env var in the test, restore it after), returns `null`. Given a signed-in user not in the list, returns `{ error }`. Given no signed-in user at all, returns `{ error }`. Given an admin email with different casing/whitespace than the allowlist entry, still matches (proves `normalizeEmail` is actually being used, not a raw string compare) — this is a real regression risk given Module 5.1's own history with email normalization.
- `isNearCap`: `count` at exactly 80% of `cap` → `true`; just under → `false`; `cap === null` → always `false` regardless of `count`.
- `onAttempt` in `withKeyFailover` (in `app/tests/unit/key-pool.test.ts`, existing file or new): given a pool where the first key rate-limits and the second succeeds, `onAttempt` is called twice, once per slot, in order — proves the hook fires on every attempt, not just the final one. Given every key fails, `onAttempt` is still called once per attempted slot even though the overall call throws.
