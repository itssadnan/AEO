## Read this first — lessons from Modules 5.4 and 5.5's delegations (apply these here, don't repeat them)

Modules 5.4 and 5.5 were each built by an external model, then independently verified by Claude against real ground truth (compiler, live database, live API calls, a real Vercel deployment) rather than trusted at face value. Both had real, working code that still contained genuine defects — some only a live run could catch. This module goes through the exact same independent verification, so avoiding these same mistakes will save a round trip. Every item below is a real thing that actually happened on this project, not a hypothetical.

1. **A self-report is not evidence, even when the underlying code is right.** 5.5's delegate wrote a summary claiming it created a `visibility_explanations` table; the actual migration file correctly created `visibility_snapshots` — the code was fine, the delegate's own description of its own work was wrong. Don't narrate from memory at the end; re-read the actual file before describing what it does.
2. **Read the exact instruction, don't approximate it.** 5.5's spec required updating a specific table (the `visibility_snapshots` row in the ERD's "Full column reference" table) with a specific column list. The delegate instead added a different, unrelated — but individually correct — ERD fix (a missing relationship line) and never touched what was actually asked for. Fixing something real doesn't satisfy an instruction to fix something else. If you fix an unrelated issue you notice along the way, do both — don't substitute one for the other.
3. **Never invent a field, prop, or interaction not in this spec.** 5.5's delegate added an unrequested `explanationBreakdown` parameter and an invented numeric confidence-threshold rule to a prompt whose exact text this spec's predecessor had already fully specified. If you find yourself adding a prop, a design element, a copy string, or a color not listed below, stop — either it belongs in a section of this spec (add it there and say so in your report) or it's out of scope (flag it, don't add it unasked).
4. **Don't duplicate an existing shared utility.** 5.5's delegate gave `parse-explanation-response.ts` its own local `AiProviderError` class instead of importing the one shared class the rest of the codebase already uses (`@/lib/ai-providers/errors`) — it happened to work by accident (structural typing), but would have silently broken any `instanceof` check elsewhere. Before writing a new component, hook, or type, check `app/src/components/` (once it exists, see below) and `app/src/lib/` for one that already does this.
5. **Spec-provided reference material can itself be wrong — cross-check it against something already proven to work, don't just trust it because it's written down.** 5.5's own spec (written by a prior Claude session) confidently handed the delegate reference SQL containing two real bugs: a Postgres construct that's outright invalid (`aggregate function calls cannot contain window function calls`) and a call to a Supabase Vault function that doesn't exist (`vault.decrypt(...)`, when the real, working API is `vault.decrypted_secrets`). Both were copied in verbatim and both slipped past `tsc`/`eslint`/careful spec-diffing — neither check runs the code. **This spec has been through that same live-execution pass already, but treat every code sample in it the same way anyway: if something looks off, say so in your report rather than assuming a spec author already checked it.**
6. **A green build is not the same as a correct render.** Module 5.2's real, documented incident: a Client Component imported a barrel file that also re-exported server-only code. `tsc`, `eslint`, and every unit test passed. The actual Vercel production build failed for five consecutive deploys before anyone caught it, because none of those checks execute a real Next.js build — only Vercel's own build does. This is now a standing Definition-of-Done item (`progress/progress.json` → `definitionOfDone` → `deploy`) for exactly this reason, and it is *especially* relevant to this module: this is the first module that puts real Client Components in front of real Server Component data-fetching at scale. Say plainly in your report that you could not run a real Next.js build (this sandbox's `next build` SIGBUSes — see Module 0.0) and that this check is Claude's job in verification, not something you can claim passed.
7. **Never let the frontend recompute a number the backend already computed.** This is the same principle 5.5's spec was built around (`run_visibility_scoring_cycle()` computes every score/percentage/ratio once, in SQL, specifically so nothing downstream has to re-derive it) — it applies here too, one layer up. If `visibility_snapshots.score` is `78`, render `78`. Never write client-side logic that recalculates a percentage, a rank, a ratio, or a trend direction from raw rows when the field already exists on the row. If a display needs a number this module's tables don't already have, that's a gap to flag, not a reason to compute it yourself in a `.tsx` file.
8. **A checklist item is only checked if you have real evidence for it.** Paste actual command output (`tsc --noEmit`, `eslint`, `npm test`), not a description of expected output. For anything you cannot verify without live infrastructure (a real Vercel preview, a real screenshot of a rendered page), say so explicitly rather than describing what you expect it would look like.

## Design system (read fully before writing a single component)

This section is the product's actual competitive differentiation, not decoration — take it as seriously as the SQL in 5.5's spec. Do not substitute your own visual judgment for what's written here; if you think something below is wrong, flag it in your report rather than quietly designing around it.

### Why these specific choices — the competitive context

The spec docx (Section 2.3) names nine direct competitors already live in this category: KIME, Profound, Peec AI, Semrush AI Toolkit, Otterly.AI, Nightwatch, SE Visible, AirOps, Searchable — plus smaller indie entrants. Section 2.3 is explicit that there is no technology moat in this space; the playbook (send prompts to AI engines on a schedule, parse mentions, report them) is identical across all of them. **That means the dashboard experience itself is one of the few places this product can actually differentiate**, alongside the Trust & Transparency principle (Section 3.5) neither Profound nor Peec AI lead with as hard as this spec requires. Concretely, from direct research into this category as of mid-2026:

- **Profound** (`tryprofound.com`) is the enterprise-grade leader — near-black UI (`#08090A` theme color), dense, agent/workflow-oriented, built for teams that need "enterprise reporting, prompt intelligence, and agent-style workflows." Reviewers call its dashboards clean but built for scale, not a daily 30-second glance.
- **Peec AI** (`peec.ai`) is the closest structural analog to this product: a four-area dashboard (dashboard / prompts / sources / competitors — nearly identical to this module's five-view split) that reviewers consistently praise as clean and fast to read ("simple enough that you can tell what's happening in under a minute"). Its documented weakness, repeated across multiple independent reviews: it **overwhelms first-time users** with dense metrics and no guided onboarding, forcing new users to "invest significant time experimenting rather than extracting insights immediately."
- **Otterly.AI** leads with a single benchmark number — the "Brand Visibility Index" — specifically so customers get one clear answer instead of scattered prompt-level results, before anything else.
- Broader 2026 SaaS-dashboard research (Linear, Vercel, Stripe, Notion, Supabase, Raycast, Sentry as the most-cited reference set) converges on the same pattern regardless of category: **progressive disclosure**. Show the one number that answers "is everything OK?" first; put density one click away. Linear's own dashboard is the canonical example — a clean list by default, analytics and burndown charts sit under a separate "Insights" view. Dark-mode-first is now the default expectation for daily-use B2B tools in this cohort, with a **true dark grey base (roughly `#0E`–`#1A` range), never pure black** — pure black against light text causes halation and eye strain on a screen people check every day.

**The synthesis this module should execute on:** Otterly's one-number confidence + Linear's progressive disclosure + Peec's proven five-way structural split (which this product already has, acceptance-criteria-mandated) + Profound's premium dark-UI polish — **explicitly fixing Peec's most-cited weakness** by treating first-run/empty states and the "How we calculated this" transparency panel as first-class, designed screens, not afterthoughts. That combination is not represented by any single competitor today; building it well is the actual design brief.

### Color system

Dark mode is the default and the primary design target; light mode must also work (do not skip it) but dark is what every screenshot, empty state, and component below is designed against first.

Define these as CSS custom properties in `app/src/app/globals.css`, replacing the current placeholder `--background`/`--foreground` pair, using Tailwind v4's `@theme inline` block (already the pattern in this file — extend it, don't replace the mechanism):

```
--color-surface-0   #0B0D10   /* page background, dark mode */
--color-surface-1   #12151A   /* card/panel background */
--color-surface-2   #1A1E24   /* raised elements: modals, dropdowns, the "How we calculated this" drawer */
--color-border      #262B33   /* all hairline borders — never pure white/black at any opacity */
--color-text-primary    #F4F5F6
--color-text-secondary  #9AA1AC
--color-text-tertiary   #666D78   /* timestamps, metadata, disabled states */

--color-accent          #6E5BFF   /* primary accent — violet-indigo. Deliberately not blue: nearly every SaaS analytics tool defaults to blue, and this category's leaders (Profound, Peec) both lean neutral/dark rather than colorful, leaving room to actually stand out */
--color-accent-hover    #8172FF
--color-accent-muted    #6E5BFF1A   /* accent at ~10% opacity, for subtle backgrounds (selected tab, active nav item) */

--color-positive        #34D399   /* score/rank improving, "ahead" states */
--color-positive-muted  #34D3991A
--color-negative        #FB7185   /* score/rank declining, "behind" states — never pure red (#FF0000), this is a rose tone consistent with the rest of the palette */
--color-negative-muted  #FB71851A
--color-warning         #FBBF77   /* free-plan limits, locked states, degraded/retrying jobs */

--color-engine-gemini      #6E5BFF   /* reuse accent — Gemini is the primary engine in MVP */
--color-engine-nvidia-nim  #34A0A4   /* a distinct teal, reserved for anything visibly attributed to the NVIDIA NIM-powered Explanation Engine, so customers can tell at a glance which claims came from which engine — directly serves the Section 3.5 requirement that every result is labeled by source */
```

Light mode (`prefers-color-scheme: light`, or the manual toggle's light state — see "Theme toggle" below): invert the surface scale to near-white with the same relative contrast steps (`#FFFFFF` / `#F7F7F8` / `#EEEFF1` surfaces, `#0B0D10`-family text), keep the accent and semantic colors identical — they're already accessible on both backgrounds by construction (check contrast against both surface-0 values before finalizing, don't just eyeball it).

**Never hardcode a hex value in a component.** Every color reference in `.tsx` files goes through a Tailwind class backed by the `@theme inline` variables above (e.g. `bg-surface-1`, `text-text-secondary`, `text-positive`) — this is what makes the light/dark toggle and any future rebrand a CSS-only change, not a grep-and-replace across components.

### Typography

`app/src/app/layout.tsx` already loads Geist Sans and Geist Mono via `next/font` (check this file — if the fonts aren't already wired into the `<html>` element's class list, that's a pre-existing gap to fix, not invent a new font choice for). Use them as follows, replacing `globals.css`'s current `font-family: Arial, Helvetica, sans-serif` fallback entirely:

- **Geist Sans** — all UI text: labels, body copy, navigation, buttons, the AI-answer and explanation prose text.
- **Geist Mono**, with `font-variant-numeric: tabular-nums` — every number that represents data: the Visibility Score, mention counts, percentages, ranks, dates/timestamps in the "How we calculated this" panel. This is deliberate, not a style flourish: tabular figures in a monospace face are what make a column of numbers (Share-of-Voice percentages, a competitor comparison table) actually scannable at a glance, which is the entire point of the progressive-disclosure Overview. Apply this via a `font-mono tabular-nums` utility combo, not inline styles.

Scale (Tailwind's default type scale is sufficient — do not introduce a custom one): headline numbers (Visibility Score on Overview) at `text-5xl font-semibold`, section headings at `text-lg font-semibold`, body/table text at `text-sm`, metadata/timestamps at `text-xs text-text-tertiary`.

### Spacing, radius, elevation

- Border radius: `rounded-xl` (12px) for cards/panels, `rounded-lg` (8px) for buttons/inputs/badges, `rounded-full` for avatars and status dots. Do not mix in a third radius value anywhere.
- Elevation: this design system uses **borders, not shadows**, to separate surfaces (`border border-border` on every card) — consistent with the Linear/Vercel/Supabase reference set, and it's what keeps a dark UI from looking muddy (shadows barely read on dark backgrounds; a one-pixel lighter border does). The one exception: the "How we calculated this" drawer and any dropdown/popover get a real `shadow-xl` in addition to their border, since those float above other content and need the extra separation.
- Page layout: a persistent left sidebar (workspace switcher, the five view links, plan-tier badge, settings/sign-out) plus a main content area capped at `max-w-6xl` with responsive padding — not full-bleed. Match `app/src/app/brands/new/page.tsx`'s existing `max-w-*` container pattern rather than inventing a new layout primitive.

### Component inventory — build these once, in `app/src/components/ui/`, reuse everywhere

This is a **new folder** not yet documented in `docs/CONVENTIONS.md`'s Section 1 folder structure. Add it there as part of this module's deliverable (one paragraph: "`app/src/components/` holds presentation-only, cross-view UI primitives with no data-fetching or business logic of their own — analogous to `src/modules/` for business logic, but for UI"). Every component here takes plain props and fetches nothing itself; all data fetching happens in Server Components in `app/src/app/`.

- **`Card`** (`app/src/components/ui/card.tsx`) — the base surface primitive (`bg-surface-1 border border-border rounded-xl p-6`). Every panel on every view is a `Card` or built from one.
- **`MetricStat`** — big number + label + optional trend indicator (`↑`/`↓` in `positive`/`negative` color + a percentage-point delta, e.g. "+4 pts this week"). Powers the Overview's headline Visibility Score and its secondary stats row. Takes the trend direction and delta as props already computed by the caller — never computes them itself (lesson #7 above).
- **`EngineBadge`** — a small pill showing which engine produced a result (`bg-engine-gemini` or `bg-engine-nvidia-nim` background at low opacity, colored text/dot, label text e.g. "Gemini Visibility" or "NVIDIA NIM Explanation"). This is the literal implementation of the Section 3.5 "explicitly labeled by source" requirement — every score and every explanation on every view renders one of these next to it, no exceptions.
- **`PlanBadge`** — free/starter/growth/agency pill, used in the sidebar and Settings.
- **`CalculationDisclosure`** — the "How we calculated this" pattern. An info-circle icon button next to any score or explanation; clicking it opens a slide-over panel (`Drawer`, below) showing: the exact prompt text, provider + model, timestamp, the full raw AI answer (rendered as plain escaped text, never `dangerouslySetInnerHTML` — CONVENTIONS.md Section 6, rule 5), extracted entities (brand mentioned, competitors found, position), and citations with their domain-type classification. Build this **once** as a shared component parameterized by a `CalculationSource` prop shape (see "Data shapes" below) — every view that shows a score reuses the exact same component and prop shape; do not build a bespoke version per view.
- **`Drawer`** — a generic right-side slide-over (used by `CalculationDisclosure` and nothing else needs inventing a second one).
- **`LockedPanel`** — wraps content that's gated to paid plans: renders the real panel underneath at reduced opacity with a `backdrop-blur-sm` overlay, a lock icon, one sentence of what's behind it, and an "Upgrade" CTA button. This is the standard SaaS paywall pattern (blurred-preview-plus-CTA, not a blank box) and is what satisfies the acceptance criterion that locked panels are "never silently omitted" — the customer can see there's real value there, just not read it yet.
- **`EmptyState`** — icon/illustration slot + headline + one sentence + optional CTA. Every view needs one for its own "no data yet" case (see below) — build it generically once, pass view-specific copy in.
- **`DataTable`** — a plain, accessible table primitive (header row, sortable-by-click column headers where noted below, row click-through) for the Prompt Explorer's response history and Competitor Explorer's Share-of-Voice table. No pagination library — server-side `LIMIT`/`OFFSET` via search params is sufficient at this data volume (see caching/data-fetching pattern below).
- **`Tabs`** — the top-level five-view navigation and Competitor Explorer's internal Share-of-Voice / Explanation / Opportunities sub-tabs. A plain accessible tabs implementation (radio-group pattern with `role="tablist"`), no external dependency needed for something this simple — do not add a component library dependency for this.

### Theme toggle

A three-state toggle (System / Dark / Light) in Settings, persisted via a cookie read in a Server Component (so the correct theme applies on first paint, no flash-of-wrong-theme) — not `localStorage` alone, which cannot be read before first client render in a server-rendered app. Default to dark when no cookie is set yet (matches "dark is the default" above), falling back to `System` only once the user has explicitly chosen it.

### Empty and first-run states — designed, not defaulted

Every view must have a real, designed empty state for "this brand has no data yet" — given current live data (one real `visibility_snapshots` row in the whole database as of this spec being written), **this is not an edge case, it is what the product looks like for every new customer on day one**, and it's the exact failure mode Peec AI is criticized for. Concretely:

- **Overview**, no snapshots yet: replace the headline `MetricStat` with an `EmptyState` reading approximately "Your first Visibility Score will appear here once your first check completes" with a sub-line naming the actual mechanism (checks run on a schedule / a Free-plan on-demand check) — not a blank card, not a skeleton loader pretending data is coming any second.
- **Prompt Explorer**, no `check_runs` yet: `EmptyState` pointing at Settings to configure prompts if none exist yet, or "first check is queued" if prompts exist but no runs have landed.
- **Competitor Explorer**, no competitors configured: `EmptyState` directing to Settings. No competitors *and* no snapshot: same Overview empty state, contextualized.

## Architecture decisions

**Server Components fetch, Client Components interact — the existing `brands/new/` split, applied consistently.** Every view's `page.tsx` is an `async` Server Component that queries Supabase directly (via `createSupabaseServerClient()`, already in `app/src/lib/db`) and passes plain serializable props down. Client Components (`"use client"`, suffixed `-client.tsx` or colocated per existing convention) exist only where real interactivity is needed: the `Tabs` selection, the `CalculationDisclosure` drawer open/close state, the theme toggle, table sort-column clicks. This keeps the client bundle small and — directly relevant after Module 5.2's real incident — makes it structurally hard to accidentally pull a server-only import into client code, since almost nothing is a Client Component in the first place.

**No client-side data fetching, no SWR/React Query.** Every view's data need is known at request time from the URL (`workspaceId` from the session, optional `brandId`/date-range search params) — plain Server Component `fetch`/Supabase queries with Next.js's data cache (see caching below) cover every case in this module. Do not add a client-fetching library; it would duplicate caching machinery Next.js already provides here and reintroduce the "does the UI show a stale/inconsistent number" risk lesson #7 above is about.

**Caching: Next.js `unstable_cache` (or the stable tag-cache API available in this Next.js version — check `next@16.2.11`'s current API before assuming which one, do not guess) tagged per-brand, invalidated by a `revalidateTag` call.** Per `docs/CONVENTIONS.md` Section 4's explicit rule for this module ("Dashboard aggregates... computed once when a new check result lands, cached, invalidated by tag when new data arrives — never recomputed on every page view"). Concretely: every read in this module is tagged `brand:${brandId}`. The actual invalidation trigger (calling `revalidateTag` when a new `visibility_snapshots` row lands) is **out of scope for this module** — it belongs to whichever process writes that row (5.5's `scoring-worker` and/or a future webhook), and it currently doesn't exist. Flag this explicitly in your report as a cross-module gap rather than either building it yourself (out of scope, would touch Module 5.5's Edge Function) or silently shipping with no invalidation path at all. For this module's own deliverable: implement the tagged reads and a documented `revalidateBrandCache(brandId)` helper (`app/src/lib/cache.ts`) that the eventual caller will invoke — write it, export it, don't wire it up to anything yet.

**Route structure**, using Next.js's route groups (parentheses don't affect the URL, matching the existing `(auth)` group's pattern):

```
app/src/app/(dashboard)/
  layout.tsx              Sidebar + top-level Tabs nav, workspace/auth guard (mirrors dashboard/page.tsx's current auth check)
  overview/page.tsx
  prompts/page.tsx                       Prompt Explorer, list view
  prompts/[promptId]/page.tsx            Prompt Explorer, single-prompt drill-down + response history
  competitors/page.tsx                   Competitor Explorer
  reports/page.tsx
  settings/page.tsx
  settings/brands/[brandId]/page.tsx     brand/prompt config -- reuses app/src/app/brands/new/'s existing form patterns, does not duplicate them
```

The existing `app/src/app/dashboard/page.tsx` placeholder is replaced: its auth-check logic (get user, get memberships, get workspaces) moves into `(dashboard)/layout.tsx` as the shared guard for every view under it, and `/dashboard` itself becomes a redirect to `/overview`. Delete the placeholder's inline workspace-list rendering — that becomes the sidebar's workspace switcher instead, not a standalone page.

## Data shapes this module reads (read-only — do not write to any of these tables)

Every field below is already computed by 5.4/5.5; this module renders them, never recalculates them (lesson #7).

```typescript
// From visibility_snapshots, most recent row per brand for Overview,
// full history for trend lines. See docs/architecture/entity-relationship-diagram.md
// and app/supabase/migrations/0016_visibility_scoring_and_explanation.sql for the
// authoritative shape -- this is a read-side summary, not the source of truth.
type VisibilitySnapshot = {
  id: string;
  periodStart: string; // date
  periodEnd: string;
  score: number; // 0-100, already computed -- render directly
  mentionCount: number;
  avgRank: number | null;
  shareOfVoice: {
    totalChecks: number;
    brand: { name: string; mentionCount: number; sharePct: number };
    competitors: { name: string; mentionCount: number; sharePct: number }[]; // already sorted desc
  };
  sourceInfluence: { domainType: string; citationCount: number; pct: number }[];
  explanationSkipReason: "free_plan" | "no_competitor_ahead" | null;
  status: "not_applicable" | "queued" | "processing" | "retry" | "completed" | "failed";
  // Paid-only, null unless status = 'completed':
  explanationBreakdown: {
    competitorName: string;
    citationRatio: number;
    explanationText: string; // AI-generated prose -- render as plain text, never dangerouslySetInnerHTML
    breakdown: { domainType: string; pct: number }[];
  } | null;
  opportunityGaps: {
    domainType: string;
    competitorCitationCount: number;
    competitorPct: number;
    brandCitationCount: number; // always 0 by construction, see 5.5's decisions log
  }[];
  recommendedActions: { action: string; confidence: "high" | "medium" | "low"; rationale: string }[] | null;
};

// The CalculationDisclosure component's one prop shape, reused everywhere a
// score/result needs a "how we calculated this" expansion:
type CalculationSource = {
  promptText: string;
  provider: "gemini" | "nvidia_nim";
  model: string;
  checkedAt: string; // timestamptz
  rawAnswer: string; // plain text, escaped by default JSX rendering
  extractedEntities: {
    brandMentioned: boolean;
    positionAmongCompetitors: number | null;
    competitorNamesFound: string[];
    citedDomains: string[];
    citedDomainTypes: { type: string }[];
  };
};
```

## Per-view specification

### Overview (`(dashboard)/overview/page.tsx`)

The daily-glance view — one screen, no scrolling required at a typical laptop viewport for the primary content (a "Recent activity" list below the fold is fine to scroll to).

- Headline `MetricStat`: the latest `VisibilitySnapshot.score` for the brand, trend delta vs. the previous snapshot, an `EngineBadge`, and a `CalculationDisclosure` icon.
- Secondary stats row (three `MetricStat`s, smaller): raw mention count, average rank, Share-of-Voice (brand's own `sharePct`).
- A trend line/sparkline across the brand's snapshot history (period end date on X, score on Y) — a simple SVG line chart is sufficient, no charting library needed for one series at this data volume; if you judge a library is genuinely warranted, flag it in your report rather than adding a dependency unasked (lesson #3).
- **Free-plan workspaces**: an additional stat card, "Experiments used: N of 3" (from `workspaces.experiments_used`), and once `N = 3`, replace any "run a new check" action with an upgrade CTA — per the acceptance criteria, existing report data must remain fully visible regardless (this only affects the ability to trigger a *new* check, never read access to what already exists).
- Empty state per "Empty and first-run states" above.

### Prompt Explorer (`(dashboard)/prompts/page.tsx` + `prompts/[promptId]/page.tsx`)

- List view: every active prompt for the brand, each row showing the prompt text, last-checked timestamp, and a small mention/no-mention indicator for its most recent `check_extractions` row.
- Drill-down view: the full AI Response History timeline for one prompt — a reverse-chronological `DataTable` of every `check_runs`/`check_extractions` pair for that prompt, each row expandable (or linking) to the full raw answer + `CalculationDisclosure` data. This is explicitly "what did it say on July 20 vs. today" per the spec docx — make the date/time comparison easy, e.g. a simple date-range filter on the table, not a fully custom diff view (out of scope, not requested).

### Competitor Explorer (`(dashboard)/competitors/page.tsx`)

Three `Tabs`: **Share-of-Voice** (always visible, all plans), **Why They Win** (the Explanation Engine output), **Opportunities** (the Opportunity Finder).
