## Fixes required

### 1. Wire the UI in for real (highest priority — the module currently has no visible surface)

`app/src/app/(dashboard)/reports-view.tsx` accepts a `crawlAudit: CrawlAuditRow | null` prop (added last pass) but never imports or renders `CrawlAuditTrigger` anywhere in its JSX — confirmed by grep, zero usages in the file. The whole feature is dead code in production today.

- Import `CrawlAuditTrigger` from `./crawl-audit-trigger` in `reports-view.tsx`.
- Render `<CrawlAuditTrigger brandId={brand.id} websiteUrl={brand.website} initialAudit={crawlAudit} />` as its own `Card` section, placed directly above the existing "Scheduled Reports" card (per the original spec's Dashboard integration section — do not move or touch any other existing section).
- After this fix, paste the actual JSX diff in your report so it's obvious the render call exists, not just the prop.

### 2. Fix the audited bot list

The original spec was explicit: `AUDITED_BOTS = ["GPTBot", "PerplexityBot", "ClaudeBot", "Google-Extended", "CCBot"]`, verbatim, "do not add or substitute a different bot list." The shipped code uses `["Googlebot", "GPTBot", "Claude-Web", "PerplexityBot", "CCBot"]` instead — two bots are wrong:
- `Google-Extended` (governs whether Gemini can use a site's content — directly relevant to this product, which tracks Gemini-grounded search) was replaced with `Googlebot` (the regular search crawler, unrelated to AI grounding).
- `ClaudeBot` (Anthropic's current crawler user-agent) was replaced with `Claude-Web` (a deprecated, different user-agent).

Fix in all three places, consistently:
- `app/src/modules/crawl-audit/types.ts` — `AUDITED_BOTS` constant (and its comment, which currently falsely claims to list "the five bots the spec requires").
- `app/src/modules/crawl-audit/fetchers.ts` — its own local `AUDITED_BOTS` constant (currently duplicated from `types.ts` rather than imported — while fixing this, also just import it from `types.ts` instead of redeclaring it, per CONVENTIONS.md's "don't duplicate a shared constant" rule).
- `app/tests/unit/crawl-audit.test.ts` — every test that asserts on `Googlebot`/`Claude-Web` needs updating to assert on `Google-Extended`/`ClaudeBot` instead. Do not just rename the string in the assertion without checking the test still expresses the right intent (e.g. the robots.txt parsing test that disallows `Googlebot` specifically should disallow `Google-Extended` instead, using a `User-agent: Google-Extended` block in its fixture robots.txt).

### 3. Implement the missing 24h cache

The original spec's Caching section (and this module's own `cachingNotes` in `progress.json`) requires: before running a fresh audit, query the most recent `crawl_audits` row for the brand; if `checked_at` is within the last 24 hours, return that row as-is (no new fetches). None of this exists — `runAndPersistCrawlAudit` in `app/src/modules/crawl-audit/crawl-audit.ts` always fetches fresh.

- Add a `getOrRunCrawlAudit(brandId, websiteUrl)` function (this is the name the original spec's Public interface section specifies) that: queries the latest `crawl_audits` row for `brandId` (reuse `getLatestCrawlAudit`, don't re-query), and if it exists and `checked_at > now() - 24h`, returns it directly without calling `runCrawlAudit`/inserting a new row. Otherwise runs the fetch-and-persist path (the existing `runAndPersistCrawlAudit` logic).
- Decide and document which of `runAndPersistCrawlAudit` (always fresh) vs `getOrRunCrawlAudit` (cache-aware) the Server Action (`actions.ts`) and the "Run Audit" button should call — per the original spec, `getOrRunCrawlAudit` is what's called from the Server Action; if you want an explicit user-triggered "force refresh, ignore cache" action too that's a reasonable addition, but call it out explicitly in your report as an addition beyond the spec, don't silently fold it in.
- Add a unit test: two calls to `getOrRunCrawlAudit` within 24h of each other result in only one set of fetches (mock `Date`/`checked_at` for the second call to simulate this, and assert `fetch` was only called 3 times total, not 6).

### 4. Add the missing checklist abstraction (pass/fail/warning + fix instructions)

The original spec required a `CrawlChecklistItem` type and a pure `buildCrawlChecklist(audit): CrawlChecklistItem[]` function (see original spec's "Shapes" and "Public interface" sections) — neither exists. Instead, `crawl-audit-trigger.tsx` inline-renders raw allowed/blocked and present/missing badges, and in particular shows llms.txt-missing in the same red/negative styling as a real failure. This directly contradicts the product spec's explicit instruction that llms.txt must never be shown as a failure, only pass/warning ("no overclaiming its impact").

- Add `CrawlChecklistItem` (`id`, `label`, `status: "pass" | "fail" | "warning"`, `fixInstructions`) to `app/src/modules/crawl-audit/types.ts`.
- Add `buildCrawlChecklist(audit: CrawlAuditRow): CrawlChecklistItem[]` to `app/src/modules/crawl-audit/crawl-audit.ts` (pure function, no I/O) that maps the stored audit into checklist items: one per audited bot (fail if blocked, pass if allowed), one for llms.txt (`pass` if present, `warning` — never `fail` — if absent, with fix text along the lines of "Optional: no major AI vendor has confirmed llms.txt affects citations yet"), one for schema.org (pass/fail), one for heading structure (pass if exactly one H1, warning if zero or multiple, with a specific fix instruction).
- Update `crawl-audit-trigger.tsx` to render from `buildCrawlChecklist`'s output (three-way pass/fail/warning badge styling, using this codebase's existing `positive`/`warning`/`negative` color tokens — reuse, don't invent new ones) instead of the current ad hoc two-color rendering.
- Unit test `buildCrawlChecklist` directly, per the original spec's Tests section: a fully-passing audit → every item `"pass"`; an audit where one bot is blocked → that bot's item `"fail"`, others unaffected; `llms_txt_present: false` → that item is `"warning"`, explicitly asserted never `"fail"` (a regression guard, the same pattern this codebase already uses for the plan-tier bug in `dashboard.test.ts`).

### 5. De-duplicate `getLatestCrawlAudit`

`app/src/modules/dashboard/queries.ts` has its own `getLatestCrawlAudit` that re-implements the same Supabase query already in `app/src/modules/crawl-audit/crawl-audit.ts`, using the `supabaseFrom(supabase, table as any)` escape hatch meant only for tables not yet in the generated `Database` type — `crawl_audits` is already in the regenerated types, so this cast is now unjustified there.

- Delete the duplicate implementation in `dashboard/queries.ts`. Import and re-export `getLatestCrawlAudit` from `@/modules/crawl-audit` instead (same pattern this file already uses for `mapPlanTier`, re-exported from `./plan-tier` a few lines below — match that pattern).
- Confirm `reports/page.tsx`'s import of `getLatestCrawlAudit` from `@/modules/dashboard/queries` still resolves correctly after this change (it should, since you're re-exporting, not removing the export).

### 6. Add the missing env var, stop hardcoding the user-agent

The original spec required a configurable `CRAWL_AUDIT_USER_AGENT` env var (default provided in code, not required to be set). The shipped code hardcodes the user-agent string directly in `fetchers.ts` instead, and `.env.example` was never updated with it (a different, unrelated pre-existing entry — `SUPABASE_SERVICE_ROLE_KEY` — was miscited in the last report as this module's `.env.example` change; it predates this module).

- In `app/src/modules/crawl-audit/fetchers.ts`, change the hardcoded `"User-Agent": "AEO-CrawlAudit/1.0 (+https://aeo.example.com/bot)"` to `process.env.CRAWL_AUDIT_USER_AGENT ?? "AEOVisibilityBot/1.0 (+crawl-readiness audit)"` (default string from the original spec — feel free to keep the existing default text instead if you prefer, just be consistent and say which you picked).
- Add `CRAWL_AUDIT_USER_AGENT` to `app/.env.example` with a one-line comment noting it's optional and has a default.

### 7. Add the workspace-membership check in the Server Action (defense in depth)

`app/src/modules/crawl-audit/actions.ts` doesn't check the caller is a member of the brand's workspace before calling the audit — RLS on `crawl_audits` still blocks unauthorized writes/reads at the DB layer (not a live data-leak vulnerability), but an unauthorized call currently surfaces a raw Postgres RLS error string to the client instead of a clean app-level error.

- Add the same membership-check pattern already used in `app/src/app/brands/new/actions.ts` (read that file first) to `runCrawlAuditAction` and `getLatestCrawlAuditAction` before they touch the database. Return a clean `{ error: "..." }` for an unauthorized caller instead of letting the RLS error string through.
